# KMS-backed Aadhaar candidates and encrypted document writes

The change replaces client-visible extracted Aadhaar digits with a masked, owner-scoped, one-use candidate, moves persisted account/member values to direct KMS ciphertext, and makes gateway document writes request the shared SSE-KMS key explicitly. Web and Expo flows carry the opaque candidate into existing GraphQL mutations, while Terraform adds the dedicated field key and storage enforcement. The dedicated candidate path has sound owner, expiry, one-use, and transaction placement, but other Aadhaar-capable ingestion and the deployment sequence do not yet preserve the same guarantees. Watch for: **[confirmed]** generic registered-document readings can persist and return unfiltered model text for Aadhaar uploads; **[confirmed]** the bucket deny policy is applied before old writers become compatible; **[confirmed]** no deployable legacy/rollback bridge supplies Fernet reads or lets the prior release read new KMS ciphertext; **[confirmed]** alternate separators bypass field redaction; **[confirmed]** any configured S3 endpoint disables encryption, not only local development; **[likely]** KMS/config failures escape local API boundaries; and **[confirmed]** one Expo account failure path retains picker cache.

**Verdict**: NEEDS_CHANGES

## High-level view

The dedicated `/extract-aadhaar` route and durable job branch reduce the client contract to ordinary KYC fields, `aadhaarMasked`, and `aadhaarCandidateId`. Consumption happens under the account/member mutation transaction, so a failed business write rolls the one-use marker back, and server defaults preserve older GraphQL documents that omit the new argument.

The generic registered-document reader explicitly recognizes Aadhaar but relies on prompt compliance rather than a deterministic output policy. Its raw model text remains part of both synchronous output and durable job results, so it bypasses the stronger dedicated flow.

The storage implementation routes both new-file and new-version puts through one SSE-KMS argument builder. The bucket-policy rollout and local endpoint exemption are the weak points: enforcement precedes compatible task rollout, other writers still omit headers, and an endpoint variable alone authorizes unencrypted storage.

The field-cipher migration reads both KMS and Fernet formats in code, but runtime configuration supplies only the KMS key. The first KMS write also crosses a rollback boundary that the previous release cannot read; the runbook warns against an incompatible rollback without defining a deployable bridge revision.

## Generic document import bypasses the Aadhaar output boundary

**High — [confirmed].** The deed prompt deliberately supports Aadhaar and asks the model to mask it (`services/api/src/ai_reading/prompts.py:236-248`), but that is a probabilistic instruction, not an enforcement boundary. `extract_registered_fields` returns both parsed fields and the full model text as `raw` (`services/api/src/ai_reading/operations.py:275-293`), while the worker invokes `secure_extraction_result` only when the operation name is exactly `extract-aadhaar` (`services/api/src/ai_reading/jobs.py:119-124`). An Aadhaar uploaded through `import-registered-document` can therefore put full digits into `document_read_jobs.result` and return them to a client whenever the model repeats or mis-masks the number. Apply deterministic identity-document sanitization before either response path and remove raw text for Aadhaar/PAN classifications; safest is to refuse identity documents on the generic importer and direct them to the dedicated path.

## Dedicated result redaction misses valid separator variants

**High — [confirmed].** `_redact_number` only allows whitespace or ASCII hyphens between digits (`services/api/src/aadhaar.py:166-172`). The allowlisted `name`, `dob`, `gender`, `address`, and `confidence` fields are then persisted and returned after that substitution (`services/api/src/aadhaar.py:175-189`). A provider value such as `1234.5678.9012`, `1234/5678/9012`, or one using a Unicode dash survives intact even though the same response’s `aadhaar` field identifies the twelve digits. Replace separator-specific matching with a scanner that compares normalized digit sequences while preserving surrounding text, or fail the extraction if any allowlisted value still contains the normalized identifier. Add adversarial punctuation and Unicode cases to the security test.

## Bucket enforcement has no safe mixed-task deployment window

**High — [confirmed].** The new bucket policy denies every `PutObject` without explicit `aws:kms` and the exact key ARN (`infra/terraform/modules/persistent/s3.tf:251-284`). Only the new gateway revision adds those request fields (`services/gateway/src/storage.py:155-169`) and routes both object-write branches through them (`services/gateway/src/storage.py:418-442`). The runbook nevertheless applies the persistent layer, including enforcement, before the runtime layer deploys the compatible gateway (`docs/runbooks/aadhaar-kms-rollout.md:72-83`). During that gap—and during ECS rolling replacement—old gateway tasks are guaranteed to fail uploads. The assistant attachment migration writer also issues `put_object` without these headers (`services/assistant/scripts/migrate_attachments.py:37-43`), contradicting the runbook’s all-writers prerequisite (`docs/runbooks/aadhaar-kms-rollout.md:55-65`). Split key/output creation from policy enforcement: create the key/output, deploy all compatible writers, prove the mixed fleet, then enable the deny policy in a separately reviewed persistent change.

## Fernet compatibility and application rollback are not deployable

**High — [confirmed].** Non-KMS ciphertext requires `AADHAAR_ENC_KEY` at read time (`services/api/src/aadhaar.py:130-145`), but the API task definition injects only `AADHAAR_KMS_KEY_ARN` and has no Fernet secret (`infra/terraform/modules/runtime/ecs.tf:287-307`; repository-wide Terraform search found no `AADHAAR_ENC_KEY`). Startup still succeeds because validation checks only the new KMS key, leaving any legacy reveal to fail after deployment. The runbook acknowledges that the Fernet inventory/key are unknown (`docs/runbooks/aadhaar-kms-rollout.md:39-49`) but the declared runtime cannot satisfy its own “do not deploy” prerequisite.

New writes immediately use the novel `kms-direct:v1:` format (`services/api/src/aadhaar.py:25,117-128`), which the pre-change Fernet-only release cannot read. The rollback section says to deploy a “previous compatible revision” and not deploy an incompatible one (`docs/runbooks/aadhaar-kms-rollout.md:111-121`), but this diff creates no earlier compatible revision or write feature flag. Add a staged bridge: first deploy a dual-reader with the legacy secret and a controllable old/new write mode, then enable KMS writes only after rollback targets are KMS-capable. Wire the retained Fernet key as a reviewed secret until reconciliation proves zero legacy rows.

## The MinIO exemption is configuration-open, not local-only

**Medium — [confirmed].** `get_storage` treats any non-empty `STORAGE_S3_ENDPOINT` as permission to construct `StorageService(..., allow_unencrypted_local=True)` (`services/gateway/src/routes/storage.py:53-77`). That suppresses the KMS requirement and all SSE-KMS headers (`services/gateway/src/storage.py:145-169`) without checking `APP_ENV` or an explicit insecure-local gate. The comment that the variable is never deployed is not a fail-closed control; configuration drift, a test endpoint, or an alternate S3 deployment silently weakens storage. Require `APP_ENV in {local,test}` plus an explicit local-only flag, and reject custom endpoints in deployed environments.

## KMS and storage configuration failures lack local domain boundaries

**Medium — [likely].** KMS SDK/base64/config exceptions propagate directly from `_encrypt_bytes`/`_decrypt_bytes` (`services/api/src/aadhaar.py:100-145`) through GraphQL mutations such as `apply_my_kyc` and both reveal mutations (`services/api/src/main.py:3047-3089,3121-3152`). Strawberry normally serializes resolver exception messages into GraphQL errors, so AWS/config details can reach clients unless a higher formatter masks them; no scoped masking is present in the reviewed hunk. Gateway construction has a parallel boundary gap: `get_storage()` runs before the upload route’s `try` (`services/gateway/src/routes/storage.py:326-356`), so a missing key does not use the route’s stable `Storage error` response. Keep transaction rollback, but translate KMS/decode/config failures to stable non-sensitive domain errors and log only safe operation identifiers; construct or validate storage inside a caught startup/request boundary.

## Expo account scans do not always remove the transient file

**Medium — [confirmed].** The account flow deletes a cache URI only after a successful candidate was created (`apps/mobile/src/app/account.tsx:109-145`). The no-candidate branch returns at lines 115-123, and the exception branch at lines 146-147 also bypasses deletion, even though the new success copy says the card was not retained. The member flow already has the correct lifecycle by deleting in `finally` (`apps/mobile/src/app/add-member.tsx:132-190`). Move the account cleanup into `finally` and test unreadable/provider-error cases as well as success.

## Focused tests miss rollback and compatibility contracts

**Low — [confirmed].** Candidate tests use a fake connection with no transaction rollback semantics and call `consume_candidate` directly (`services/api/tests/test_aadhaar_security.py:45-101,146-174`). There is no mutation-level test proving that a candidate remains usable when account/member validation, encryption, business SQL, or critical audit enqueue fails after candidate selection; no schema test sends the old GraphQL mutations without `aadhaarCandidateId`; and the S3 branch test inspects source text rather than executing each branch against a fake S3/DB (`services/gateway/tests/test_storage_encryption.py:47-51`). Add focused service tests for rollback/reuse, old GraphQL documents, KMS error redaction, generic-import sanitizer behavior, and both actual `create_file` branches.
